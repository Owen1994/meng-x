# 造场流水线改造方案

> 版本：v1.0（2026-10-22）
> 状态：待评审
> 范围：把点子铺共创产物从「九格产品话术」升级为「经用户异步参与 + 主理人一次确认，即可交给 AI 编程工具施工的完整施工包」
> 关联文档：《点子铺-产品设计方案.md》《法学备考功能实施设计.md》《法学助手-RAG-后续工作.md》

---

## 1. 背景

### 1.1 项目定位演进

meng-x 已完成三段演进：拾梦（梦境日记，已废弃，仅留小程序空壳）→ 点子铺（功能共创）→ 当前形态：**仙官「百晓仙君」单前台 + `ChannelRegistry` 注册表路由 + 多通道道场**。法学备考助手是第一个建成的道场（18 部法律 4042 条法条入库并 100% 向量化、三路 RRF 检索、对话式出题判分、实时画像），新能力接入成本已被注册表架构压到「加一条通道，路由零改动」。

### 1.2 产品初衷与闭环断点

初衷是一个自生长闭环：

```
用户使用中提出仙官欠缺的能力
  → 仙官与用户共创设计
  → 产物含完整产品设计 + 开发方案
  → 经简单人工干预
  → 交给 AI 完成开发
  → 新能力作为道场挂载上线
```

闭环上游已断。实测案例「文言文对喷道场（酸儒）」的九格 JSON：定位/人设/流程清楚，但**无法开工**——没有路由信号与冲突分析（酸儒语料含「罪/打人」等法学信号词，会误切法学通道）、语料来源是空头支票、无数据设计、无集成点、验收不可测、内容安全风险（微信生态一票否决）缺失。

### 1.3 对照样板

法学道场之所以能落地，是因为开发者人工补做了《法学备考功能实施设计.md》：架构映射、DDL、换挡机制、防幻觉三道防线、分期排期、风险预案。**这份人工文档正是闭环里缺失的中间产物**。本方案的本质：把它的生产过程系统化，且让原题用户在其中异步参与。

**根因**：两种目标互斥的产物（对用户的产品稿、对 AI 的工程包）被压在同一条「反技术」流水线上；信息上限 = 用户的嘴；没有代码事实输入；没有质量闸门；agent 之间没有契约与工具。不是模型不够聪明，是工序与输入结构性缺失。

## 3. 目标与非目标

### 3.1 目标

1. 一张 `scale=应用`、状态 ACCEPTED 的卡，经异步工部流水线 + **用户在造物线异步决策 + 主理人一次终审**，产出自包含《施工包》：AI 编程工具据此能在现有技术栈完成一期开发并编译通过。
2. 施工包必含：通道登记（可直接贴入 `ChannelRegistry`）、集成点与 SSE 事件、数据设计 DDL、后端/前端改动清单、语料与外部依赖、风险（含内容安全）、任务 checklist、可逐条核对的验收条目。
3. 技术决策与当前代码一致：信号查重、类名/包名/事件协议真实存在。法学道场作为回归基准——用新流程重放，产物结构应与现有 law 包实际形态吻合。
4. 用户在工部期间可异步参与产品/口味/合规取向决策；主线对话不中断；多条造物线可并行存在。
5. 不牺牲前殿访谈体验：九格流程、锦囊预取延迟、仙官人格不变。

### 3.2 非目标

- 不做 AI 自动写代码/自动上线；工部终点是施工包（远期扩展见 §15）。
- 不改造前殿实时回路的调用次数与延迟。
- 不做通用代码生成器/通用脚手架，只服务 meng-x 道场模式。
- 不扩九宫格（扩格加重访谈，且关键格仍会被议程跳过）。
- 不动小程序壳与部署链路。

## 4. 总体设计：双回路

│ 回路 B：工部（异步工单，可挂起等人；一张应用卡一条工单 + 一条造物会话）                    │
│                                                                                         │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐                 │
│   │ 需求分析师 │→│ 领域顾问  │→│ 架构师    │→│ 审校官    │→│ 主理人终审 │→ 排版官 → 施工包 │

│                             ▼                   ▼                                        │
│                    ┌────────────────┐   确定性校验工具（代码，非模型）：                   │
│                    │ 用户（造物会话） │   信号查重/符号存在性/字段完整/命名冲突/可测性       │

- **回路 A 沿用、仅改名归位**：仙侠皮只留在仙官对用户的表达；后台 prompt 角色名改职能名（议程调度官 / 设计书记员），消除「名实不符」的角色暗示。
- **回路 B 全部新建**，关在新包 `com.mengx.server.forge` 内，前殿与法学通道零风险。
- 功能级小卡（`scale=功能`）仍走现有 PRD 格式化老路；回路 B 只服务应用卡。

## 5. 用户参与模型：身外身与造物线

### 5.1 两个仙官

- **主会话（前台仙官）**：现有聊天页，行为不变，可同时聊任何话题。
- **造物会话（身外身）**：每张在制应用卡一条卡级会话。仙官以分身形态出现，口吻自称与本体一致，用户明确知道「这位正在造 XX 道场」。工部各岗产出的问题由**传话工序（herald）**用仙官口吻转述，用户永远看不到星君/黑板/JSON。

### 5.2 问题三分流（去零门槛承诺后的纪律）

| 问题类型 | 处理 |
|---|---|
| 产品/口味/合规取向（杠人的尺度、开场白风格、哪些话题绝不碰、语料自己给还是 AI 生成、验收试玩确认） | **问用户**：进造物会话，WAITING_USER |
| 技术决策（信号冲突、DDL、事件复用、类清单） | 不问用户：架构师给方案，写进施工包，主理人终审拍板 |
| 成本/外部 key/上线 | 问主理人：WAITING_OWNER，看板处理 |

能给合理默认的问题不问人，默认值标注「（仙官代拟）」进终审；每岗挂起追问 ≤ 2 轮。

### 5.3 异步触点

- 用户不在线不阻塞：问题挂起为 `WAITING_USER` 状态，前端轮询取角标；用户下次打开或下次与仙官聊天时可见、可答。
- **两线互相感知**：主会话上下文注入该用户各工单待决问题摘要；主线聊到该道场时仙官可引导跳转造物线。
- 用户超时（默认 72h 可配）不答：有默认值的按默认推进并在终审标注；无默认值的保持挂起，终审由主理人兜底。
- 采纳、上线知会复用现有感谢卡/修为墙/署名机制，不新增 push。

### 5.4 快照隔离与版本

- 开工时冻结九格为 `design_snapshot`，版本号 `design_version`，工部全程只认快照。
- 用户在造物线的决策性回答 → 升版本，工单反常从挂起岗重跑。
- 主线后续聊出的新九格内容不直接进入在制包：终审前提示「设计稿有变更（重跑/沿用快照）」；终审后到达的进二期 backlog。

## 6. 工部 Agent 协作架构

### 6.1 黑板模式，不是圆桌

- agent 之间禁止直接对话。每个 agent 只读黑板上游段、只写自己负责的段（`owns` 声明，编排器运行时断言）。
- 编排器（代码，不是 agent）掌握流程：每岗返回四态指令 `CONTINUE / WAIT / REWRITE(目标岗, 原因) / BLOCK`。
- 起草与审校分岗；审校官只看产物 + 代码事实，不看架构师推理过程。
- 打回硬上限 2 轮，超限转 BLOCKED 上看板；每工单设总调用次数/token 预算（复用 llm_usage_log 统计）。

### 6.2 ForgeAgent 抽象

在现有 `AgentRunner` 之上新增薄接口层（编排不写进 AgentRunner）：

```
interface ForgeAgent {
    String name();                     // analyst / advisor.legal / architect / reviewer / herald
    List<String> reads();              // 黑板读段
    List<String> owns();               // 黑板写段（唯一写者）
    List<Class<?>> tools();            // 只读工具，可为空
    AgentResult run(ForgeContext ctx); // 产物 POJO + 四态指令 + 待问用户问题
}
```

- 调用内核升级为 langchain4j **AiServices**（同一已引入依赖 1.18.0，不新增框架）：`@Tool` 挂只读工具、POJO 直出结构化契约（替代手写剥围栏）、限流退避沿用 AgentRunner 现有逻辑。
- 注册：照 `ChannelRegistry` 模式建 `AgentRegistry`；领域顾问按道场类型注册（`advisor.legal` / `advisor.default`…），新类型 = 加一条，编排器零改动。
- 用量打标：`LlmUsage.set("forge.analyst" / "forge.advisor.*" / "forge.architect" / "forge.reviewer" / "forge.herald")`。

### 6.3 岗位编制（首期 4+2）

| 岗位 | 读黑板 | 写黑板 | 工具 | 说明 |
|---|---|---|---|---|
| 需求分析师 analyst | 九格快照 | 产品深化段、待决问题 | 无 | 流程补异常/退出分支；边界拆 兜底/误退场/合规拒答/隐私；验收 String→可测条目数组；人设补正反例话术；数据工具补 来源/冷启动/更新/成本；卡背补 successMetrics、complianceNotes；openQuestions |
| 领域顾问 advisor.* | 产品段 | 领域设计段 | 领域范例库（只读） | 插拔：legal=教学设计（题型轮换/真题参照/掌握度/防幻觉三防线）；default=强制语料方案 + 内容安全 |
| 架构师 architect | 产品段+领域段+架构手册 | 工程施工包段 | 手册读取、源码召回、注册表查询、符号 grep（全只读） | 见 §6.5 契约 |
| 审校官 reviewer | 全量黑板 | 审校段、REWRITE 指令 | 确定性校验工具集（§6.4） | 代码级硬阻断 + 模型级挑刺 |
| 传话 herald | 待决问题 | 造物会话消息 | 无 | 把结构化问题渲染成仙官口吻 + 选项；用户回答经它回写黑板（用户只感知仙官） |
| 排版官 formatter | 终稿黑板 | 施工包 Markdown | 无 | 由现有 IdeaPrdService 改造，保持「不新增设计」，容量放宽至 60000 字 |

### 6.4 确定性工具（代码实现，禁止交给模型）

1. `SignalConflictTool`：通道 id/signals 与 `ChannelRegistry` 全量条目查重（含子串碰撞，覆盖法学约 60 个信号词）。
2. `SymbolExistsTool`：施工包引用的类名/包名/SSE 事件/消息 role 在代码库 grep 存在性。
3. `SchemaCompleteTool`：施工包 required 字段完整性。
4. `DdlConflictTool`：表名/列名与现有库冲突检查。
5. `AcceptanceTestabilityTool`：验收条目数 ≥3 且不含「稳定/尽量/大概」等不可测词（词典规则）；合规段强制非空。

## 7. 工单状态机与执行模型

### 7.1 状态

`RUNNING`（某岗模型执行中）/ `WAITING_USER` / `WAITING_OWNER` / `REVIEW`（待主理人终审）/ `BLOCKED` / `DONE` / `FAILED` / `CANCELLED`。

### 7.2 转移

```
开工 → RUNNING(analyst)
RUNNING → CONTINUE → RUNNING(下一岗)
RUNNING → WAIT(问题) → WAITING_USER / WAITING_OWNER
回答提交 → RUNNING(挂起岗，带答案重跑；designVersion 升级)
architect 完成 → reviewer：代码校验失败 → REWRITE(归属岗，≤2轮)；超限 → BLOCKED
审校 PASS → REVIEW(主理人)
主理人确认 → formatter → DONE；主理人打回 → 指定岗重跑
卡被谢绝/删除 → CANCELLED
模型异常重试耗尽 → FAILED（可从断点手动重试）
```

### 7.3 执行纪律

- **无长事务、无线程等待**：模型调用不得阻塞等人。resume 是事件驱动的普通异步任务（回答到达 / 手动重试 / 开机恢复时触发）。
- **先落盘后交棒**：答案与每岗产物先持久化，再触发下一岗，任意时刻杀进程可重放。
- **重启恢复**：应用启动时扫描 `RUNNING` 超时（如 >30 分钟）的工单，从 `stage` 断点重跑（模型岗天然幂等：只认黑板输入重写本岗段）。
- **串行队列**：同一账户模型执行排队（已有并行撞限流 1302 的教训，`IdeaCounselService.java` L135）；WAITING 不占执行名额，故 N 条造物线可并行挂起。
- 幂等：回答接口按 questionId 幂等，防多端重复提交。

## 8. 数据模型

沿用 `ddl-auto=update` 加字段（加列必须带 default，项目已有 PG NOT NULL 加列教训，见 `IdeaSessionEntity.java` L35-L38）；建表规范写入手册，Flyway 统一迁移另行立项。

### 8.1 新表 forge_jobs（一条应用卡一条工单）

```sql
create table forge_jobs (
  id                bigserial primary key,
  card_id           bigint not null unique,
  status            varchar(20) not null default 'RUNNING',
  stage             varchar(30),                          -- analyst/advisor.*/architect/reviewer/format
  design_version    int not null default 1,
  design_snapshot   text not null,                        -- 冻结版九格 JSON
  stage_payload     text,                                 -- 黑板：施工包信封 v1
  pending_questions text,                                 -- 挂起问题数组 JSON（id/岗/类型/选项/默认值/截止时间）
  rounds            int not null default 0,
  error_note        varchar(500),
  created_at        timestamptz not null default now(),
  updated_at        timestamptz not null default now()
);
```

### 8.2 现有表扩展

- `idea_sessions` 加：`kind varchar(10) not null default 'MAIN'`（MAIN/FORGE）、`card_id bigint null`、`forge_job_id bigint null`。
- `idea_messages`：造物线用户/分身消息正常写（role=user/assistant）；工部内部消息沿用 counsel 模式，role = `forge.analyst / forge.advisor / forge.architect / forge.review / forge.herald`，正文为 JSON 信封，支持单岗重跑与审计。
- `idea_cards` 加：`build_status varchar(20) not null default 'NONE'`、`build_json text`、`build_generated_at timestamptz`；与 prdStatus 平行，不动现有状态机与 PRD 功能。
- 信封 JSON 一律带 `version`；Jackson 维持 `FAIL_ON_UNKNOWN_PROPERTIES=false`（项目既有模式）。

## 13. 风险与对策

| 风险 | 对策 |
|---|---|
| 架构手册腐化、施工包与代码漂移 | 手册入 git；评审 checklist 加「手册随改」；二期源码 RAG 校正；符号存在性工具兜底 |
| 多岗串联失败/错误级联 | 入口 schema 校验不合格直接打回不进模型；工部失败显式上抛（不像锦囊静默降级）；单岗可重跑 |
| 模型编造不存在的类/事件 | 只读手册与召回片段中出现的符号；SymbolExistsTool 硬校验 |
| 无限追问/成本失控 | 每岗挂起 ≤2 轮、打回 ≤2 轮、工单总预算封顶；scene 级用量入 llm_usage_log |
| 多端/并发重复回答 | questionId 幂等；黑板分段唯一写者 + 编排器断言 |
| 功能卡被复杂化 | 回路 B 严格限定 scale=应用；功能卡维持现有 PRD 路径 |
| 工部一期工具越权 | 工具全部只读（grep/检索/查询），无写文件、无执行能力 |
| langchain4j API 版本差异 | 开工前先冻结 AiServices/@Tool/POJO 返回的 1.18.0 方法签名（先写最小 spike 编译通过，再批量实现） |

## 14. 技术选型结论

- **不引入任何新框架**，pom 零新增。
- langchain4j 从「只用 ChatModel 内核」升级为使用同依赖的 **AiServices**（@Tool、POJO 输出）；自研 ZhipuChatModel 实现的是 langchain4j ChatModel 接口，天然兼容。
- 不迁 Spring AI（与自研 `llm/` 三档模型、SSE 桥接、用量双写大面积重叠，迁移零收益）。
- 不引入 Temporal/Camunda/Spring StateMachine：当前状态 ≤8 个、岗 ≤5 个、一张 PG 表 + 开机扫描即可表达；待岗数 >10、出现并行分支 join、工单量达每日数百时再评估 Temporal。
- 前端不引入路由库/状态库。

## 15. 远期：实施 Agent（本方案之后的独立阶段）

工部稳定后，以同一编排框架挂接「实施 agent」：工具从只读升级为受控写——改文件、`mvn compile`、跑测试；编译/测试失败带错误自动回到实施岗。前置条件：沙箱工作区、git 分支与回滚、测试闸门、爆炸半径隔离。与工部「出文档」量级不同，严禁与本期混做。终点愿景：**用户共创 → 工部造包 → 主理人确认 → AI 实施 → 注册表挂道场上线**，自生长闭环全程贯通。
