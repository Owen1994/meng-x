# 造场流水线改造方案

> 版本：v1.2（2026-10-22）
> 状态：已定稿
> 变更：v1.1 补充 §5.5 主理人介入方式（看板操作、不进聊天线）与终审六项职责；
> v1.2 评审定稿：① 施工包定位降为架构级（三层分工：施工包=关键架构/手册=全局约束/AI 工具=细节 how），撤 SymbolExistsTool、DdlConflictTool；② AiServices 改道编排式工具（自研 ZhipuChatModel 无工具协议、智谱端无 JSON schema）；③ 权限简化：不设角色，看板可见即可操作；④ 删 72h 超时推进，WAITING_USER 无限期暂停、无定时任务；⑤ 造物线聊天走独立接口物理隔离（`/forge/jobs/{jobId}/chat/stream`），answer 接口合并；⑥ herald 职责定为形态路由（答案回抛出岗消化，一岗一轮一问）；⑦ 信号冲突只检测不消解；⑧ §7 落定执行宿主细节：专用线程池参数、状态-线程解耦模型（等用户=零线程占用的 DB 行）、resume 三触发源、CAS 防重入；⑨ §9 落定消息下发模型：后台只写库不推、前端轮询、方案 A 确认即关流
> 范围：把点子铺共创产物从「九格产品话术」升级为「经用户异步参与 + 主理人一次确认，即可交给 AI 编程工具施工的完整施工包」
> 关联文档：《点子铺-产品设计方案.md》《法学备考功能实施设计.md》《法学助手-RAG-后续工作.md》

## 1. 背景

### 1.1 项目定位演进

meng-x 已完成三段演进：拾梦（梦境日记，已废弃，仅留小程序空壳）→ 点子铺（功能共创）→ 当前形态：**仙官「百晓仙君」单前台 + `ChannelRegistry` 注册表路由 + 多通道道场**。法学备考助手是第一个建成的道场（18 部法律 4042 条法条入库并 100% 向量化、三路 RRF 检索、对话式出题判分、实时画像），新能力接入成本已被注册表架构压到「加一条通道，路由零改动」。

### 1.2 产品初衷与闭环断点

初衷是一个自生长闭环：

```
用户使用中提出仙官欠缺的能力
  → 仙官与用户共创设计
  → 产物含完整产品设计 + 开发方案
  → 经简单人工干预
  → 交给 AI 完成开发
  → 新能力作为道场挂载上线
```

闭环上游已断。实测案例「文言文对喷道场（酸儒）」的九格 JSON：定位/人设/流程清楚，但**无法开工**——没有路由信号与冲突分析（酸儒语料含「罪/打人」等法学信号词，会误切法学通道）、语料来源是空头支票、无数据设计、无集成点、验收不可测、内容安全风险（微信生态一票否决）缺失。

### 1.3 对照样板

法学道场之所以能落地，是因为开发者人工补做了《法学备考功能实施设计.md》：架构映射、DDL、换挡机制、防幻觉三道防线、分期排期、风险预案。**这份人工文档正是闭环里缺失的中间产物**。本方案的本质：把它的生产过程系统化，且让原题用户在其中异步参与。

## 3. 目标与非目标

### 3.1 目标

1. 一张 `scale=应用`、状态 ACCEPTED 的卡，经异步工部流水线 + **用户在造物线异步参与 + 主理人一次终审**，产出自包含《施工包》：**架构级**（模块划分、集成点、表级数据设计、通道登记、任务拆分、风险验收），不深入类名/签名等代码细节——配合《架构手册》作为全局约束，AI 编程工具据此在现有技术栈完成一期开发并编译通过。三层分工：**施工包=关键架构 what、手册=全局约束、AI 编程工具=细节 how**。
2. 施工包必含：通道登记（可直接贴入 `ChannelRegistry`）、集成点与 SSE 事件、数据设计（表级 DDL 草案）、后端/前端改动清单（职责粒度）、语料与外部依赖、风险（含内容安全）、任务 checklist、可逐条核对的验收条目。
3. 终点验收：产出正常可用的施工包/PRD，开发略微评估修改后即可交由 AI 编程工具按方案生成代码；不要求严格按法学道场重放对照（法学实施设计仅作 advisor few-shot 黄金范例与架构参照）。
4. 用户在工部期间可异步参与产品/口味/合规取向决策；主线对话不中断；多条造物线可并行存在。
5. 不牺牲前殿访谈体验：九格流程、锦囊预取延迟、仙官人格不变。

### 3.2 非目标

- 不做 AI 自动写代码/自动上线；工部终点是施工包（远期扩展见 §15）。
- 不改造前殿实时回路的调用次数与延迟。
- 不做通用代码生成器/通用脚手架，只服务 meng-x 道场模式。
- 不扩九宫格（扩格加重访谈，且关键格仍会被议程跳过）。
- 不动小程序壳与部署链路。

## 4. 总体设计：双回路

```
┌─────────────────────────── 回路 A：前殿（实时，每轮对话） ───────────────────────────┐
│ 用户 ⇄ 仙官（主会话）                                                                  │
│   每轮：议程调度官（原产品星君）→ 设计书记员（原工造星君）→ 九格快照（counsel 信封）     │
│   炼卡 → 功能卡（功能/应用）→ 看板 → 采纳（ACCEPTED）                                   │
└───────────────────────────────────────┬───────────────────────────────────────────────┘
                                         │ 应用卡「开工」
┌───────────────────────────────────────▼───────────────────────────────────────────────┐
│ 回路 B：工部（异步工单，可挂起等人；一张应用卡一条工单 + 一条造物会话）                    │
│                                                                                         │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐                 │
│   │ 需求分析师 │→│ 领域顾问  │→│ 架构师    │→│ 审校官    │→│ 主理人终审 │→ 排版官 → 施工包 │
│   └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘  └──────────┘                 │
│        └─────────────┴──────┬──────┘            │ 打回（≤2轮）                            │
│                             ▼                   ▼                                        │
│                    ┌────────────────┐   确定性校验工具（代码，非模型）：                   │
│                    │ 用户（造物会话） │   信号查重/符号存在性/字段完整/命名冲突/可测性       │
│                    │ 仙官「身外身」   │                                                │
│                    └────────────────┘                                                │
│                                                                                         │
│         黑板：施工包 JSON（forge_jobs.stage_payload，分段唯一写者）                        │
```

- **回路 A 沿用、仅改名归位**：仙侠皮只留在仙官对用户的表达；后台 prompt 角色名改职能名（议程调度官 / 设计书记员），消除「名实不符」的角色暗示。
- **回路 B 全部新建**，关在新包 `com.mengx.server.forge` 内，前殿与法学通道零风险。
- 功能级小卡（`scale=功能`）仍走现有 PRD 格式化老路；回路 B 只服务应用卡。

## 5. 用户参与模型：身外身与造物线

### 5.1 两个仙官

- **主会话（前台仙官）**：现有聊天页，行为不变，可同时聊任何话题。
- **造物会话（身外身）**：每张在制应用卡一条卡级会话。仙官以分身形态出现，口吻自称与本体一致，用户明确知道「这位正在造 XX 道场」。**分身人设为裁剪版（约 150 字）**：自称与本体一致 + 明确「正在造 XX 道场」+ 只答工部问题 + 闲聊引导回主线——不复用完整 HOST_PROMPT（收藏架/本场卡/愿望引导/九格议程全部无关）；工部各岗产出的问题由**传话工序（herald）**用分身口吻转述，用户永远看不到星君/黑板/JSON。造物线**旁路主线全套**：不跑路由器、法学检索、双星、锦囊、提炼器（用户答「可以」是确认工部问题，不是确认炼卡）。

### 5.2 问题三分流（去零门槛承诺后的纪律）

| 问题类型 | 处理 |
|---|---|
| 产品/口味/合规取向（杠人的尺度、开场白风格、哪些话题绝不碰、语料自己给还是 AI 生成、验收试玩确认） | **问用户**：进造物会话，WAITING_USER |
| 技术决策（信号冲突、DDL、事件复用、模块划分） | 不问用户：架构师给方案，写进施工包，终审拍板 |
| 成本/外部 key/上线 | 上看板待办（v1 无角色区分，看板可见即可操作） |

能给合理默认的问题不问人，默认值标注「（仙官代拟）」进终审；每岗挂起追问 ≤ 2 轮；**一岗一轮只挂一个问题**（多问题拆多轮，异步不阻塞，避免一条自由文本同时回答多个问题）。

**答案归属铁律**：用户回答永远路由回**抛出该问题的岗**（pending_questions 带岗归属字段，状态机单岗串行结构上不存在错路由空间），prompt 形态为「你之前问了 X，用户答了 Y（原文），结合黑板继续」——**语义消化是归属岗的专业职责，herald 只做形态路由不做内容理解**。

### 5.2.1 自由发言处理（herald 形态路由，窄场景触发）

仅当**有挂起问题且用户走文本输入**时触发意图识别（点选项按钮零歧义不需要）；glm-4-flash 三分类，错误分最坏多一轮引导、不污染黑板：

| 判定 | 处理 |
|---|---|
| 在答挂起问题 | 原文 + 问题原文交归属岗带答案重跑 |
| 新需求/吐槽 | 记 backlog（不触发重跑），分身引导拉回挂起问题：「已记下，终审一并考虑；先把手头这个定了？」 |
| 无关闲聊 | 分身礼貌挡回主线：「此处专司营造 XX 道场，想叙话主线见」——**引导用户而非被用户带偏** |

工单 RUNNING 中用户插话：不打断执行中的岗（竞态噩梦），消息落库 + 记 backlog，当前岗跑完后 herald 统一处理。

### 5.3 异步触点

- 用户不在线不阻塞：问题挂起为 `WAITING_USER` 状态，前端轮询取角标；用户下次打开或下次与仙官聊天时可见、可答。
- **两线互相感知**：主会话上下文注入该用户各工单待决问题摘要（**上限 3 个工单、每个 50 字**，防止 system prompt 膨胀）；主线聊到该道场时仙官可引导跳转造物线。
- 用户超时不答：**无限期暂停（v1 不做超时推进、无定时任务）**——工单停在 WAITING_USER 等人，用户从任务列表看到「等你拍板」才去处理；有默认值的问题终审时主理人可代拍。
- 采纳、上线知会复用现有感谢卡/修为墙/署名机制，不新增 push。

### 5.4 快照隔离与版本

- 开工时冻结九格为 `design_snapshot`，版本号 `design_version`，工部全程只认快照。
- 用户在造物线的决策性回答 → 升版本，工单从挂起岗重跑。v1 简化失效传播：**挂起点之后的所有岗整体重跑**（不做段级版本/失效标记——工单短，重跑成本可承受；段级失效待工单变长后再议）。
- 主线后续聊出的新九格内容不直接进入在制包：终审前提示「设计稿有变更（重跑/沿用快照）」；终审后到达的进二期 backlog。

### 5.5 主理人介入方式：看板操作，不进对话

主理人**不是任何聊天线的参与方**。两条会话线（主会话、造物会话）都只存在于用户与仙官之间；主理人的介入点全部是看板上的结构化操作，每条决策直接写入黑板与审计记录（谁、何时、基于哪版稿子拍板）：

- **看板待办**：成本/key/上线类问题以条目形式上看板，填选项或短答案，非对话。
- **终审（REVIEW）**：在「施工包」页签阅读摘要后执行三动作——批准（→ 排版官 → DONE）/ 打回（必须指定岗位与原因，定向重跑）/ 搁置谢绝（→ CANCELLED）。BLOCKED 工单与无默认值的挂起问题也在此裁决。

**v1 权限口径**：不设角色体系，看板可见即可操作（信任圈既有设计的延续）；后期需要时再加 users.role 控权，接口与 UI 已按「终审按钮全员可用」设计，届时仅需加校验。

终审判六件事（机器判不了的取舍；机械正确性已由审校官代码闸保证）：

1. 产品方向：深化稿是否忠于用户原意，补写内容有无跑偏；
2. 代拟项：所有「（仙官代拟）」默认值逐条认或改；
3. 技术方案知情放行：entryMode、事件复用/新增、建库与向量化、任务拆解；
4. 合规与风险：内容安全定级（一票否决，complianceNotes 非空才准入终审）；
5. 成本与外部依赖：模型档位、调用频率、语料来源、key 与环境变量；
6. 一期范围：tasks 分期合理性、验收条目可核对性。

正常路径下终审预期为数分钟阅读 + 一次确认；若每次都需大改，说明上游 prompt 或确定性校验失效，应修流水线而非让主理人当编辑。

## 6. 工部 Agent 协作架构

### 6.1 黑板模式，不是圆桌

- agent 之间禁止直接对话。每个 agent 只读黑板上游段、只写自己负责的段（`owns` 声明，编排器运行时断言）。
- 编排器（代码，不是 agent）掌握流程：每岗返回四态指令 `CONTINUE / WAIT / REWRITE(目标岗, 原因) / BLOCK`。
- 起草与审校分岗；审校官只看产物 + 代码事实，不看架构师推理过程。
- 打回硬上限 2 轮，超限转 BLOCKED 上看板；每工单设总调用次数/token 预算（复用 llm_usage_log 统计）。

### 6.2 ForgeAgent 抽象

在现有 `AgentRunner` 之上新增薄接口层（编排不写进 AgentRunner）：

```
interface ForgeAgent {
    String name();                     // analyst / advisor.legal / architect / reviewer / herald
    List<String> reads();              // 黑板读段
    List<String> owns();               // 黑板写段（唯一写者）
    List<Class<?>> tools();            // 只读工具，可为空
    AgentResult run(ForgeContext ctx); // 产物 POJO + 四态指令 + 待问用户问题
}
```

- 调用内核**沿用 AgentRunner 模式**（v1.2 改道，不上 AiServices）：AiServices 的两大卖点本项目均不可用——POJO 直出依赖模型端 JSON schema（智谱不支持），@Tool 依赖 ChatModel 工具协议（自研 ZhipuChatModel 未实现 tools 传参/tool_calls 回传，补齐约一天量级且收益有限）。**编排式工具效果等价**：编排器（代码）在岗前/岗后显式调用只读工具，结果拼进下一岗 prompt；围栏剥离+解析重试沿用 AgentRunner 已验证链路。远期待工具数量膨胀（>10 个）再补 tool 协议切 AiServices。
- 注册：照 `ChannelRegistry` 模式建 `AgentRegistry`；领域顾问按道场类型注册（`advisor.legal` / `advisor.default`…），新类型 = 加一条，编排器零改动。
- 用量打标：`LlmUsage.set("forge.analyst" / "forge.advisor.*" / "forge.architect" / "forge.reviewer" / "forge.herald")`（forge.* 全链路显式 set，不依赖 sceneOf 兜底推断）。

### 6.3 岗位编制（首期 4+2）

| 岗位 | 读黑板 | 写黑板 | 工具 | 说明 |
|---|---|---|---|---|

## 7. 工单状态机与执行模型

### 7.1 状态

`RUNNING`（某岗模型执行中）/ `WAITING_USER` / `WAITING_OWNER` / `REVIEW`（待主理人终审）/ `BLOCKED` / `DONE` / `FAILED` / `CANCELLED`。

### 7.2 转移

```
开工 → RUNNING(analyst)
RUNNING → CONTINUE → RUNNING(下一岗)
RUNNING → WAIT(问题) → WAITING_USER / WAITING_OWNER
回答提交 → RUNNING(挂起岗，带答案重跑；designVersion 升级)
architect 完成 → reviewer：代码校验失败 → REWRITE(归属岗，≤2轮)；超限 → BLOCKED
审校 PASS → REVIEW(主理人)
主理人确认 → formatter → DONE；主理人打回 → 指定岗重跑
卡被谢绝/删除 → CANCELLED
模型异常重试耗尽 → FAILED（可从断点手动重试）
```

### 7.3 执行宿主：专用线程池（ForgeExecutor）

工部所有岗执行与 resume 触发跑在**独立线程池**上，与 SSE 的 boundedElastic、主线请求线程完全隔离，互不抢占：

| 项 | 取值 | 理由 |
|---|---|---|
| core / max | 2 / 4 | 单机部署、工单串行语义（同一工单单岗），瞬时并发需求低；压并发是 1302 限流的既有教训 |
| 队列 | 有界，容量 200 | 工单量级小，正常远达不到；满载说明异常积压 |
| 拒绝策略 | CallerRuns | 提交点只有「答案到达 / 手动重试 / 开机恢复」三种，绝不能丢任务；队列满时由提交线程代跑（表现为该次聊天流确认变慢，可接受） |
| 岗任务超时 | Future 10 分钟 cancel → 工单标 FAILED | 模型调用自身有 ZhipuApi 超时兜底，岗任务整体超时防僵死（如网络半开） |
| 线程命名 | forge-executor-N | 日志可辨（配合 traceId 观测工部链路） |

**任务形态**：一次提交 = 一个「岗执行」任务（读黑板上游段 → 模型调用 → 写本岗段 → 状态转移 → 触发下一岗提交），分钟级完成即归还线程。**线程池里不存在任何「等待」**——不 sleep 轮询、不 wait 用户、不 hold 长事务。

### 7.4 状态-线程解耦模型

工单状态是**数据库里的一行**，不是内存里的活线程。两者的对应关系：

| 工单状态 | 线程占用 | 谁推进 |
|---|---|---|
| RUNNING（某岗执行中） | 1 个线程，分钟级 | 岗任务自己（跑完转下一态并提交下一岗） |
| WAITING_USER / WAITING_OWNER | **0**——静止的 DB 行，挂多久都零资源 | 用户（答案到达触发 resume） |
| REVIEW / BLOCKED / DONE / FAILED / CANCELLED | 0 | 终审操作 / 手动重试 / 不推进 |

**resume 触发源枚举**（全部事件驱动，无定时器）：① 造物线答案到达（chat/stream 内 herald 判定为回答后提交）；② 手动重试接口；③ 开机恢复钩子（启动时一次性扫描 RUNNING 超时 >30 分钟的工单，从 `stage` 断点重跑——模型岗天然幂等：只认黑板输入重写本岗段）。

**防重入（并发防护）**：同一工单可能双触发源并发（用户刚答完提交 resume、又点了重试）。状态转移用**条件 UPDATE（CAS）**实现：`update forge_jobs set status='RUNNING', stage=? where id=? and status='WAITING_USER'`，affected=0 说明已被其他触发源拿走，本方直接丢弃——保证同一工单任一时刻最多一个岗在跑，不需要分布式锁。

### 7.5 执行纪律

- **无长事务、无线程等待**：模型调用不得阻塞等人（「等人」只存在于 DB 行，见 §7.4）；**无任何定时任务**（不超时推进，见 §5.3）。
- **先落盘后交棒**：答案与每岗产物先持久化，再触发下一岗，任意时刻杀进程可重放；FAILED 保留 `stage` 断点，retry 从该岗重跑（上游黑板段完好）。
- 同一用户多工单的模型调用依赖 AgentRunner 既有 1302 退避兜底（v1 不做 per-user 全局串行队列，限流冲突概率低且已有退避）。
- 幂等：挂起问题的「已答」状态即幂等闸（已答问题再收到的消息按自由发言三分类处理），防多端重复提交。

## 9. 接口清单（REST，JWT 复用现有鉴权；v1.2 收敛为 8 个）

**聊天物理隔离（v1.2 核心变更）**：造物线聊天走独立接口，`/api/idea/chat/stream` 只服务 MAIN 会话（IdeaChatService 零改动零回归）；两侧 Controller 按 session.kind 做防御性校验，传错 400 防止消息落错库。SSE 事件协议（thinking/chunk/done/error）两线共用，前端渲染组件零改动。

**消息下发模型（v1.2 定稿）**：工部后台线程**从不直接向前端发消息，只写库**（黑板段 + idea_messages），前端靠轮询感知——SSE 连接生命周期 = 一次请求，工单跨小时/天存活，任何 HTTP 连接都扛不住，落库+轮询是唯一正确形态（锦囊预取同构先例）。答案提交的收尾采用**方案 A**：chat/stream 内完成 herald 三分类 + 分身确认「好，这就去继续营造」即关流；resume 在后台跑，新挂起问题以分身消息落库、前端轮询可见（一问一答一关流，与主线语义一致，用户答完即走，角标亮了再回来）。二期 `/events` 长连接补齐推送：后台岗完成推 `{jobId, questionId}` 通知事件（是通知不是聊天内容），前端拉消息渲染。

## 10. 前端设计

- 现架构为 chat/board 两视图条件渲染、无路由库，新增第三个视图 FORGE，不引入路由。
- **会话切换状态**：Chat 组件加 `viewMode`（main/forge）+ `viewForgeJobId` 指针；**切造物线不动主 session 指针**，切回主线无缝恢复（是平行视图切换，不是场次切换）；消息列表/气泡/输入区/thinking 等子组件两线复用，仅 SSE 调用函数分流（`streamIdeaChat` / `streamForgeChat`，底层 fetch+ReadableStream 抽公共）。
- 聊天页边缘一排「创造中」图标（分身剪影 + 道场名）：N 个在制工单 = N 个图标，有待决问题时呼吸动画 + 角标数字；点击切对应造物线。
- **全局轮询 hook（App 级 10~15s `/forge/pending`）**：任何视图、任何 MAIN 场次下都可见角标——「任何聊天窗口都可以去回路 B」的载体；登录/登出时管理轮询生命周期。
- 造物线视觉：工坊/营造中底色，分身气泡标注「身外身·造 XX」；问题优先渲染为**选项按钮**（点击即带问题标记走 chat/stream，零歧义），也允许自由文本（触发 herald 三分类）。
- 可随时切回主线，问题常驻不催；主线仙官引导跳转造物线。
- 看板卡详情新增「施工包」页签：状态流、通道登记、DDL、任务 checklist、缺口单、终审按钮（v1 全员可见可操作）。
- 九格面板与主聊天交互不动。**历史面板只列 MAIN 场次**（§8.2 会话管理口径）。

| herald 三分类分错（答问题/新需求/闲聊） | 错误分最坏多一轮引导，不污染黑板；选项按钮为主路径，文本输入才走分类 |
| langchain4j AiServices 不可用（POJO 直出依赖模型端 JSON schema、@Tool 依赖 ChatModel 工具协议，自研 ZhipuChatModel 未实现） | v1.2 已改道编排式工具（AgentRunner 链路）；远期工具 >10 个再补 tool 协议（ZhipuApi 加 tools 传参/tool_calls 回传，约一天量级） |
| 无限追问/成本失控 | 每岗挂起 ≤2 轮、打回 ≤2 轮、工单总预算封顶；scene 级用量入 llm_usage_log |
| 多端/并发重复回答 | 挂起问题「已答」状态闸（已答再收按自由发言三分类）；黑板分段唯一写者 + 编排器断言 |
| 功能卡被复杂化 | 回路 B 严格限定 scale=应用；功能卡维持现有 PRD 路径 |
| 工部一期工具越权 | 工具全部只读（检索/查询），无写文件、无执行能力 |

## 14. 技术选型结论

- **不引入任何新框架**，pom 零新增。
- langchain4j 维持「只用 ChatModel 内核」现状：AiServices 不可用（POJO 直出依赖模型端 JSON schema，智谱不支持；@Tool 依赖 ChatModel 工具协议，自研 ZhipuChatModel 未实现）——v1.2 改道**编排式工具**（AgentRunner 链路+编排器显式调用），效果等价零新协议；远期工具 >10 个再给 ZhipuApi 补 tool 协议（约一天量级）后切 AiServices。
- 不迁 Spring AI（与自研 `llm/` 三档模型、SSE 桥接、用量双写大面积重叠，迁移零收益）。
- 不引入 Temporal/Camunda/Spring StateMachine：当前状态 ≤8 个、岗 ≤5 个、一张 PG 表 + 开机扫描即可表达；待岗数 >10、出现并行分支 join、工单量达每日数百时再评估 Temporal。
- 前端不引入路由库/状态库。

## 15. 远期：实施 Agent（本方案之后的独立阶段）

工部稳定后，以同一编排框架挂接「实施 agent」：工具从只读升级为受控写——改文件、`mvn compile`、跑测试；编译/测试失败带错误自动回到实施岗。前置条件：沙箱工作区、git 分支与回滚、测试闸门、爆炸半径隔离。与工部「出文档」量级不同，严禁与本期混做。终点愿景：**用户共创 → 工部造包 → 主理人确认 → AI 实施 → 注册表挂道场上线**，自生长闭环全程贯通。
